## 機能ごとに具体例から進める

BDDの考え方を取り入れ、利用場面の具体例を検討し、Issueに「前提（Given）・操作（When）・期待結果（Then）」を記載する。最初の確認ケースを自動テストにし、実装とレビューまでを一つの変更で進める。Markdownに書いただけのシナリオは実行済みテストとは扱わない。CucumberやGherkin用ランナーの導入は現段階では必須にしない。

例：前回の予報を表示している状態で再取得が失敗したら、前回の行と失敗表示を確認でき、再試行で回復できる。この挙動を画面のテストと受入確認に対応させる。

#5は表示・取得状態まで。次の候補は「気温や概要で絞り込む」「列レイアウトを保存・復元する」で、必要になった時点で各シナリオとIssueを具体化する。蔵書一覧#3でも同じ進め方を使う。部品・クラス単位だけでIssueを分割せず、一つの操作が使えるところまで確認する。

参考：[CucumberのBDDの説明](https://cucumber.io/docs/bdd/)

## 仕様と実装の扱い

仕様案には、利用場面・HTTP契約・初期データ・期待結果を記載した。着手時に対象Issueの採用範囲を確認し、変更が必要なら理由と受入条件を更新する。Issueを作っただけで、未確定の貸出期間や予約運用まで採用したことにはしない。

実装者は受入条件を読み、最初に確認したいケースをテストとして書き、処理を実装して結果を確認する。AIは設計の相談とコードレビュー、詰まった箇所の説明・修正を担当できる。実装をAIへ任せる範囲はその都度の依頼に従う。

文書中のクラス名や分割は設計例。動作の条件と技術制約を守る別案も、責任・依存方向・テストの理由を説明できれば比較する。

## その後の候補

蔵書一覧を確認した後、Layout・Filterの保存復元、サーバー側検索、認証・認可、一冊の貸出、対象Loanの返却、延滞確認バッチを小さく進める。

貸出期間、冊数上限、利用不可の扱い、認証方式は該当機能の前に具体化する。予約・購入希望は追加候補。未確定の条件を埋めるためだけに大量の実装Issueを先に作らない。
