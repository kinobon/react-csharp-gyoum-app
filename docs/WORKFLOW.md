# 役割分担と開発の進め方

更新日：2026-10-01

このプロジェクトでは、ユーザーが作るものと学習の方向を決め、一つの会話のAIがドメインエキスパート役とフルスタックテックリード役を順番に担当する。役割は検討する視点を示す。同じAIによる検討を、別の専門家による独立した検証や合意とは扱わない。

最初に[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md)を読み、対象のIssue・仕様と実際のファイルを確認する。業務の案は[イベントストーミング](modeling/event-storming.md)と[ドメインモデル](modeling/domain-model.md)を参照する。

## 1. 各役の責任と判断基準

| 役 | 担当 | 責任 | 判断基準 |
|---|---|---|---|
| ドメインエキスパート役 | AIが図書館の業務担当者を演じる | 利用目的、実物の受け渡し、操作の流れ、業務ルール、例外を具体化する | 誰が何のために操作するか説明できるか。現場の流れと記録の意味がつながるか |
| フルスタックテックリード役 | 同じAI | 業務をモデル・画面・API・DB・テストへ落とし込み、小さな実装単位を作る | 学習目標を満たすか。整合性と権限を守れるか。現在の制約で実装・確認できるか |
| プロダクトオーナー兼学習者 | ユーザー | 題材、学習の優先順位、必要な業務機能、追加範囲の採否を判断する | 作るものとして納得できるか。仕組みを自分で説明・実装できるようになるか |

ドメインエキスパート役が新しく考えた規則は学習用の仮案として記録する。実際の図書館の規則を主張するときは根拠を確認し、このアプリの取り決めと区別する。

テックリード役は、API・共通ライブラリのC# 7.3、BatchのC# 14、Oracleへの生SQLアクセスなどの既存方針を守る。必要なスキルや公式資料は、実際に変更する技術に応じて参照する。

## 2. 相談・設計時の出力

役ごとの考えを次の順に短く示す。意見が食い違う場合は、理由と選択肢を残す。毎回架空の会話劇を作る必要はなく、単純な質問や修正は通常の説明でよい。

| 視点 | 示す内容 |
|---|---|
| 業務担当者役の整理 | 具体的な場面、行う操作、成功した結果、例外、仮定 |
| テックリード役の整理 | 採用候補のモデルと処理、実装範囲、受入条件、確認方法、後回しのもの |
| ユーザーが判断する点 | 題材・学習範囲・新しい業務ルールなど、実際に選択が必要な点だけ |

例：業務担当者役は「同じ本が二冊あっても、借りられた一冊だけ貸出中にする」と説明する。テックリード役は「書籍情報と各冊を分け、一冊を指定する貸出処理と二重貸出の確認を作る」と整理する。

## 3. 一つの機能を進める流れ

1. 対象の業務場面と、既に採用した条件を確認する。
2. 業務担当者役で操作・結果・例外を整理する。未確定の条件は仮案・保留として残す。
3. テックリード役で、一つの確認可能な機能と受入条件をIssue案にする。
4. ユーザーの指示と採用済みの範囲で実装し、変更に合った検証を行う。
5. 結果を確認し、採用したルールや設計変更を資料へ反映する。
6. コミット・PR・リモートへの書き込みは、ユーザーから指示された範囲で行う。

通常の技術選択、調査、文書整備、許可された範囲の実装・修正はテックリード役で進める。既に受けた指示について確認を繰り返さない。題材や学習方針を変えること、新しい業務機能を必須範囲に加えることはユーザーへ相談する。仮案を資料へ書いたことだけを採用の根拠にはしない。

AIは一つの会話で順番に検討する。別のエージェントへの分担は、ユーザーが明示的に求めた場合に検討する。

## 4. Issue案の最小形式

目的と受入条件が読める大きさにする。例えば「蔵書一覧を表示する」「一冊を貸し出す」「対象の貸出を返却する」を別々に扱う。

```markdown
## 目的
誰が何をできるようにするか。

## 範囲
今回作る操作と、後回しにする操作。

## 業務ルール
今回採用する条件と根拠。未確定の条件は仮案と明記する。

## 受入条件
具体的な初期状態・操作・期待する結果。
必要な異常系や境界値も示す。

## 検証方法
実際のスクリプト・テスト構成に合わせた確認方法。
Oracleで確認が必要な点と、未実行の検証を区別する。

## 保留事項
この機能の完成を妨げない、後続の判断や追加候補。
```

Issue案は、公開・作成の指示がなければローカルの資料または会話にまとめる。小さな変更へ不要な設計書や承認工程を追加しない。

## 5. 決定事項を残す場所

| 内容 | 記録先 |
|---|---|
| 学習方針、採用した範囲、技術制約 | PROJECT_CONTEXT.md |
| 出来事、操作の流れ、仮定、未解決の業務事項 | modeling/event-storming.md |
| 用語、関係、状態、責任の境界、確認ケース | modeling/domain-model.md |
| 一つの機能の受入条件と検証結果 | 対象Issue・PR、または作成前のローカル資料 |
| 起動方法と現在の実装状況 | README.md |

新しい判断は必要な資料へ反映し、会話だけに残さない。実装や検証の進捗を、計画の記述だけから推測しない。
